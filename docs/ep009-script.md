# AI把代码仓越写越乱，我只能停工重构

第一人称为根据开发者自述和真实仓库证据整理的口播；AI配音。

我本来想让AI帮我做个游戏。结果，游戏还没做完，我先开始考古了。

《失序之钟》的功能一直在加，仓库也被我和AI一起，整得乌烟瘴气。以前是缺什么补什么，后来是出了问题，再叠一套。

旧方案、旧设计、旧实现，都还在。看文件，每份都像能用；接新功能时，有时却又走回了旧规则。

保留历史本身没错，Git本来就干这个。问题是，现行规则、历史记录和试验方案，全挤在当前开发入口里。

然后我开始补文档。我以为写详细点，AI就能少走弯路。后来文档越来越厚，新会话进来，先得分清哪份还算数。

我查了一下，一份当前状态说明，已经十二万多字节。十九份Skills，加起来约二十五万字节。代码还没读，历史先读一大摞。

这时候，上下文不足就不只是多塞几份文件能解决的。真正该用的规则被淹没，过期信息还在争位置。

具体一次错误，还得具体查，不能都甩给模型。但版本边界连我自己都要翻半天，指望AI每次自动判断对，确实是我想简单了。

更麻烦的是，有些旧文件还真删不得。旧测试、历史回放，甚至正式资源，还在引用它们。看见legacy就全删，下一轮可能直接炸。

CI也是同款剧情。本来是帮我兜底，后来变成日常开发的主要项目。跑红了，修；修完，再跑。

有一次，当前场景已经有Boss字段，旧测试替身却没有。画面检查直接脚本报错，最后只是给测试补了个可空字段。

我想检查游戏有没有坏，结果先得修检查游戏的工具。修完一圈，进度是：终于能继续检查了。

还有一次，两路检查合计一百七十八项，都过了，汇总还是失败。两台Runner用的Python小版本不一致。这回修的是验证链自己。

这些检查不是都没用。问题是历史兼容、复杂专项和日常门禁，全挤在一条流程里。每加一层保险，就多一层要解释、要维护。

到这一步，我只能先停下新功能，做一次大规模重构。再不收拾，我自己都快接不动了。

先把一件事到底归谁管说清楚。移动、伤害、钱包、奖励，各有自己的正式入口。旧调用一起迁，别在旁边再生一个新版。

文档也分清当前、历史和实验。新会话按任务读需要的；旧证据留着查，但别默认让它把整个项目史背一遍。

日常CI已经从原来的全量一百七十九项，收成四项基础检查。复杂专项仍然保留，按修改内容跑，日常先守住最基本的功能。

架构重构和CI精简已经合入主线，文档清理还在待审。现在只能说开始还债，不能宣布从此再也不会乱。

这次最扎心的，是我自己也有份。最开始只顾着让AI快点加功能，没把有效版本、退出规则、文档和验证边界管好。

现在是真后悔，早期没把这些最基本的项目管理做好。AI写得快，历史包袱也攒得快。当时省下来的整理，后面真的得还。

项目还在继续，最近先别催新功能了。我在给自己刚写出来的祖传代码收拾屋子。你们用AI做大项目，也碰到过这种情况吗？
